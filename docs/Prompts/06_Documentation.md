# Documentation Request

## Purpose

Create or update documentation that is accurate, useful, easy to maintain, and written for someone returning to the project months later.

---

## Before Writing

1. Confirm what should be documented.
2. Read `AGENTS.md`.
3. Read `docs/Developer-Handbook/PERSONAL_RULES.md`.
4. Inspect the relevant code, files, systems, and existing documentation.
5. Identify the intended reader:
   - the project owner,
   - another developer,
   - an AI assistant,
   - or a general reader.
6. Explain which documentation files should be created or updated.
7. Mention any uncertainty or missing information.
8. Wait for approval before modifying files.

---

## Documentation Rules

- Document the current project state, not an imagined future version.
- Separate confirmed facts from assumptions or plans.
- Use simple, direct English.
- Explain technical terms when they first appear.
- Prefer examples from this project.
- Avoid duplicating the same information across multiple files.
- Link to related documentation when appropriate.
- Keep filenames, paths, commands, IDs, and code references exact.
- Do not claim that unfinished systems are complete.
- Do not remove useful existing documentation without approval.
- Do not rewrite unrelated documentation.
- Do not commit or push without explicit approval.

---

## Structure

When appropriate, use this structure:

1. Purpose
2. Responsibilities
3. Important Files
4. How It Works
5. Data or Control Flow
6. Common Problems
7. Testing or Verification
8. Related Documentation
9. Remember
10. Open Questions

Use headings, short paragraphs, lists, tables, and diagrams only when they improve clarity.

---

## Developer Handbook Rules

When updating the Developer Handbook:

- Write for “future me” returning after six months.
- Include a short beginner-friendly explanation.
- Include the deeper technical explanation when useful.
- Add a small flow diagram when the system has a clear sequence.
- Add a concise “Remember” section.
- Update the file cheat sheet when a file’s responsibility becomes clearer.
- Update the glossary when a new technical term is introduced.
- Do not change chapter structure unnecessarily.

---

## Daily Learning Log Rules

When updating the Daily Learning Log:

- Record the date.
- Summarize what was accomplished.
- Record what the project owner learned.
- Mention unresolved questions.
- State the next logical topic.
- Keep the entry concise and factual.

---

## After Writing

1. Summarize what documentation was created or updated.
2. Explain why each file changed.
3. Confirm that paths, commands, and references were checked.
4. Mention anything that could not be verified.
5. Check for duplicated or conflicting documentation.
6. Check and report the current Git status.
7. Recommend the next logical documentation task.
8. Wait for review before committing or pushing.
